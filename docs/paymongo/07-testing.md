# Payment testing plan

No payment tests were added or executed during preparation. Use project Pest rules during implementation. First-release methods are online card, GCash, Maya, QR Ph, and account-enabled Direct Online Banking through its separate Payment Intent redirect flow.

| Area                        | Scenario                                                                                                                       | Expected property                                                                                                                                                                                           |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request construction        | Server derives amount/currency from persisted order                                                                            | Client cannot lower/change amount or bind another order                                                                                                                                                     |
| Method coverage             | Card, GCash, Maya, QR Ph, each enabled DOB/Brankas bank                                                                        | Only enabled and supported methods appear; Checkout methods use Hosted Checkout and online banking uses its documented Payment Intent flow                                                                  |
| Fulfillment availability    | Each supported online method with delivery and pickup                                                                          | Online payment is selectable for both modes; existing COD/cash/card-at-store constraints remain distinct                                                                                                    |
| Fee default                 | Each enabled method                                                                                                            | Fee is absorbed; no customer surcharge appears. Any future pass-on-fee behavior requires separate approval and method-specific permission                                                                   |
| Method-specific expiry      | Each enabled Checkout and Direct Online Banking method                                                                         | Provider method/action expires according to the documented flow behavior; do not assume an undocumented card/bank window                                                                                    |
| Method expiry vs session    | Method expires while Checkout Session remains active or Payment Intent returns to a retryable state                            | Customer can retry within the 24-hour order window where supported; no automatic order cancellation or stock release from method expiry alone                                                               |
| Session closure             | Explicit expiry succeeds, rejects for paid/pending/processing, or has an unknown outcome                                       | Reconcile provider state; no premature cancellation, stock release, or replacement session                                                                                                                  |
| 24-hour cutoff              | Order reaches 24 hours with unpaid, paid, pending, processing, or uncertain provider state                                     | Reconcile and close the applicable provider flow; cancel/release stock only after confirmed terminal closure and no unresolved payment; retain stock and alert on uncertainty                               |
| QR code validity            | QR Ph code expires while its Checkout Session remains active                                                                   | Handle method expiry and retry independently from the merchant's separate order/session closure policy                                                                                                      |
| Session create              | Success, validation error, timeout, 5xx                                                                                        | Persisted attempt is recoverable; retry uses same logical idempotency key                                                                                                                                   |
| Return UX                   | Forged success query or direct return                                                                                          | Does not mutate payment/order state                                                                                                                                                                         |
| No receipt                  | Customer submits a receipt/screenshot or claims payment                                                                        | No upload is requested or accepted as proof for PayMongo; payment remains pending until provider confirmation                                                                                               |
| Provider receipt            | Successful test payment, valid email, and selected API supports receipt delivery                                               | Request the supported receipt; missing/delayed email does not change payment status or replace verified webhook processing                                                                                  |
| Signature                   | Valid test/live signature; bad/missing signature; stale timestamp; wrong mode                                                  | Only valid environment-matching request proceeds                                                                                                                                                            |
| Event semantics             | Correct paid event; unknown type; wrong session/order/amount/currency                                                          | Apply only verified, matching eligible transition                                                                                                                                                           |
| Idempotency                 | Same event repeated and concurrently delivered                                                                                 | One payment/order/inventory/sale/notification effect                                                                                                                                                        |
| Ordering                    | Duplicated, delayed, contradictory, or post-cancellation event                                                                 | No invalid regression or silent fulfillment; surfaced for reconciliation                                                                                                                                    |
| Cancellation reconciliation | Unpaid order reaches candidate cancellation point; latest provider state is paid, pending, processing, expired, or unavailable | Cancel only when provider state is reconciled and the applicable provider flow is confirmed closed; never cancel/release stock for paid or uncertain attempts                                               |
| Payment recovery            | Failed/expired attempt on an otherwise valid order; active session remains available                                           | Customer can retry within the active session; no duplicate order/session or second successful charge                                                                                                        |
| Late payment                | Provider reports success after local order cancellation                                                                        | Do not fulfill automatically; flag for operator reconciliation and an explicit refund/reinstatement decision                                                                                                |
| Refund boundary             | Customer or administrator requests a refund in first release                                                                   | No automated refund action exists; request is routed for administrator review under provider method eligibility                                                                                             |
| Recovery                    | Webhook missed/disabled, provider API unavailable, customer abandons                                                           | Safe pending state and documented operator/reconciliation route                                                                                                                                             |
| Compatibility               | New online GCash/Maya at approved cutover; historical GCash/Maya records; pickup cash/card-at-store; COD                       | Replace manual proof upload/review for new PayMongo online orders only; grandfather existing orders; retain historical records and preserve cash pickup, card-at-store, COD, fulfillment, and web/API rules |
| Persistence                 | MySQL migration with legacy records and current constraints                                                                    | Data preserved; no destructive backfill; constraints remain enforced                                                                                                                                        |

## Additional acceptance scenarios from the preparation audit

Use the G01-G12 traceability in `10-readiness-audit.md`; these are planned tests, not executed evidence.

| Scenario                                                                             | Required result                                                                                                       |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| Duplicate checkout submit from web/mobile; same token with changed payload           | Same customer/request produces the same order; mismatched reuse conflicts; stock/cart effects happen once             |
| Deadlock retries during order placement                                              | Provider mutations never run inside the retried DB callback                                                           |
| Crash before dispatch, after provider acceptance, and before saving provider ID      | Recover durable operation; no fresh key or second payable flow while uncertain                                        |
| Idempotency key older than provider retention                                        | Reconcile or escalate; no blind create retry after the key expires                                                    |
| Checkout session with failed and paid entries; multiple sequential intents           | Match the successful payment and preserve failed history; do not treat the first array item as final                  |
| Two distinct events reference one payment; two distinct payments reference one order | One normal payment application; anomalous extra money is recorded/escalated, not silently discarded                   |
| Webhook arrives before the creation response is saved                                | Durable unresolved event later reconciles to its verified flow; no metadata-only association                          |
| Inbox commit followed by enqueue failure; worker dies before/after business commit   | Sweeper/lease recovery processes pending work; no double state/stock/sale effects                                     |
| Customer/admin cancellation, method switching and cutoff race with creation/success  | Same serialization and closure contract on every path; existing URLs remain accounted for                             |
| Gateway and historical manual orders share GCash/Maya                                | Persistent origin controls proof/review and cancellation eligibility independently of rollout flags                   |
| Bank create-method/attach failure, amount outside method limit, unsupported closure  | Correct pending/recovery behavior; affected method cannot be enabled without evidence; never split charge             |
| Authenticated unknown event, signed synthetic test event, mismatched paid payload    | Unsupported events are acknowledged/ignored; paid state still requires valid local binding and authoritative evidence |
| Fresh delivery of old business event; stale signature; wrong mode; changed raw bytes | Handle verified delivery freshness separately from occurrence time; reject forgery/mode mismatch                      |
| App/browser closes, session expires, mobile return is forged, another customer polls | Order recovery after login; owner-only safe status; return URL cannot mutate payment                                  |
| Disable new gateway starts with existing payable flows                               | Existing ingress/reconciliation remains active; no reclassification as manual wallets                                 |
| Notification persistence/enqueue fails after payment commit                          | Payment stays correct; existing notification limitation is reported rather than claiming exactly-once delivery        |
| Exact amount conversion, delivery fee, integer bounds, missing provider fee/net      | No float drift; missing fee is not zero; settlement net never substitutes for payable total                           |

## Evidence layers

For worker acceptance, use the inspection and run procedure in `11-system-aligned-setup.md`: current Windows PHP lacks PCNTL. Demonstrate HTTP budgets locally; demonstrate enforced worker termination and concurrent lease recovery on a supported runtime/supervisor before claiming those properties. Do not treat `--timeout` or `--once` as proof of enforcement.

Use the actual MySQL 8.0.46/InnoDB/REPEATABLE-READ baseline and selected worker/HTTP budgets in `11-system-aligned-setup.md`. Include the existing manual refund recording/review permissions and reports in compatibility checks. Use synthetic test configuration in automated tests; root `.env` holds private developer test credentials only for authorized provider checks.

1. Unit tests for signature parser/calculation, event mapping, money conversion, and transition decisions.
2. Laravel feature tests using HTTP fakes and signed webhook fixtures; prove ownership and duplicate/race protections.
3. MySQL-specific migration/constraint validation in the supported development environment; SQLite test success alone does not prove MySQL behavior.
4. PayMongo test-mode checkout and webhook test event, only after separately authorized and configured. Never scan real QR Ph codes or use live channels.
5. Local webhook testing may use a temporary HTTPS tunnel after explicit approval; expose only the webhook route and never expose MySQL, admin tools, or secrets.
6. Human operational review of dashboard endpoint mode, delivery health, key rotation, reconciliation and launch readiness.

Automated tests, test-mode evidence, merchant activation, and live settlement each prove different things. Record exact evidence and limitations; do not claim a later layer from an earlier one.
