## Interpretation

Money Movement reference added on 2026-10-23 at developer request: [introduction](https://docs.paymongo.com/docs/money-movement-introduction), [key concepts](https://docs.paymongo.com/docs/money-movement-key-concepts). These cover wallet/transfer/settlement concepts. Customer Direct Online Banking remains governed by its Payment Acceptance resource contract; no transfer cancellation or payout event is assumed to confirm or close a checkout payment. See `11-system-aligned-setup.md` for the distinction and the verified Windows worker/scheduler limitation.

For private test-key placement, the existing Laravel service configuration pattern, verified runtime/database metadata, and the operational choices derived from this system, see `11-system-aligned-setup.md`. The [testing guide](https://docs.paymongo.com/docs/payment-acceptance-testing), [authentication reference](https://docs.paymongo.com/reference/authentication), and [webhook setup/signature guide](https://docs.paymongo.com/docs/developer-tools-webhook-setup-management) were reopened on 2026-10-23. API keys and endpoint signing secrets are separate; adding local environment entries does not implement or activate the integration.

Rechecked 2026-10-23 for the preparation audit: [online banking](https://docs.paymongo.com/docs/payment-acceptance-direct-online-banking) requires intent creation, bank Payment Method creation, attachment and redirect; its examples use different credentials by operation and list bank/amount limits. Verify each operation rather than applying one generic authentication pattern. A callable standalone bank cancellation operation was not established in this review; this remains an enablement gate, not a known endpoint.

[Webhook key concepts](https://docs.paymongo.com/docs/developer-tools-webhooks-key-concepts) specifies timely acknowledgement; use HTTP 200 JSON for compatibility. [Webhook best practices](https://docs.paymongo.com/docs/developer-tools-best-practices) says unsupported event types should be acknowledged and ignored. Our minimal durable inbox commit before acknowledgement is an application reliability requirement; do not copy the guide's acknowledge-before-enqueue sample as durable delivery. The crash and retry contracts are in `10-readiness-audit.md`.

The facts above are provider documentation statements. The scope and business rules in `02-requirements.md` onward are developer-approved project decisions; detailed schema and implementation choices remain proposals until reviewed during implementation. The authentication docs were partially dynamically rendered during review; implementation must verify the exact current reference rather than relying only on secondary examples.
