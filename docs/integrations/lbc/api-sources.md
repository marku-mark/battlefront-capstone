# Official LBC source audit

Researched 2026-10-24 using public official LBC pages only. No account was created, no merchant access was requested, and no operational API call, booking, shipment, or tracking submission was made. Consumer booking pages and the developer portal are evidence of advertised/public flows; they are not merchant API contracts.

## Flow evidence and limits

The public pages distinguish sender handoff modes (rider pickup or branch drop-off), shipment booking/details, shipping-fee settlement with LBC, shipment identifiers, parcel movement, and tracking. LBC COD/COP adds a separate buyer collection and seller remittance flow. These findings should shape the questions and domain mapping; do not copy the consumer UI as an API design.

The portal catalog’s search snippets expose names/descriptions, but direct catalog rendering does not expose the contract. A named catalog item is not proof of public access, subscription entitlement, current availability, or an API suitable for Battlefront. No endpoint path, authentication, payload/schema, sandbox host, webhook signature, cancellation contract, idempotency guarantee, or tested merchant entitlement was verified.

## Evidence levels

Keep these separate in all preparation and later implementation reviews:

1. **Public service flow:** evidenced by LBC consumer/business pages linked above.
2. **Documented API contract:** not established by this audit; requires accessible endpoint-specific official documentation.
3. **Merchant entitlement and tested behavior:** not established; requires authorized account access, verified sandbox details, and separately approved tests.

An empty/inaccessible portal view does not prove a capability is unsupported. Public flow facts do not authorize LBC contact, merchant registration, credentials, API requests, or bookings. See [capability matrix](capability-matrix.md) and [sandbox checklist](sandbox-checklist.md).
