# Purpose and activation

Plan Neo4j Aura product graphs and evidence-based PC compatibility. Use for preparation and design, not authorization to implement.

## Procedure and expected output

Read existing pc-hardware-specifications and pc-compatibility-engine skills when evaluating hardware. Inspect existing component profiles and compatibility logic before proposing a graph. Verify official Aura/Cypher documentation, free-tier capacity, lifecycle and connection limits. Model CPU, GPU, motherboard, RAM, PSU, storage and case using stable MySQL IDs and versioned manufacturer evidence. Socket alone does not prove compatibility: assess BIOS, memory generation, form factors, clearance, connectors and power where evidence exists. Distinguish compatible, incompatible and unknown. Plan parameterized bounded read queries, sync and deletion handling; never execute model-generated Cypher. Output proposed schema, query contracts, evidence matrix and unresolved scope approvals. No cloud mutations.

## Constraints

Preparation only. Do not implement integrations, edit application code or .env, install dependencies, run migrations, call Gemini, or mutate Qdrant/Neo4j. Require explicit developer approval for future implementation. Read AGENTS.md, .ai/rules/index.md and applicable rules; use graphify query before source exploration when graph exists. Keep MySQL authoritative and answers restricted to the Battlefront catalog. Preserve existing functionality and flag scope conflicts. Never expose credentials. Verify changing provider limits from official sources at planning time; do not claim multilingual quality without evaluation.
